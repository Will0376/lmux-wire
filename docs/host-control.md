# LMUX Host Control API

This document describes the structured host-side control API added for future
`lmux-mcp` integration. It is an internal local API between a trusted host
client and host `lmuxd`. It is not a public `lmux` CLI surface and does not add
target wire concepts such as MCP sessions, command tokens, cursors, transcripts,
or journals.

The existing human/legacy control socket remains in place for current commands
such as `lmux status`, `lmux term`, `lmux put`, `lmux get`, `lmux deploy`, and
`lmux boot`. The structured API is a separate listener owned by the same
`lmuxd` process and serviced by the same single `poll()` loop.

## Socket

`lmuxd` accepts an optional structured socket path:

```text
lmuxd --structured-control PATH
```

The standard host launcher currently uses:

```text
/run/lmux/control-v2.sock
```

The socket is a local Unix stream socket only. It is intended for trusted local
clients such as future `lmux-mcp`. It exposes target execution and host file
paths and therefore must not be exposed as a network service. Socket permissions
are set to `0777` by `lmuxd`, matching the existing local LMUX runtime policy
for host-created sockets under `/run/lmux`. This keeps a normal-user
`lmux-mcp` process able to connect when host `lmuxd` intentionally runs as
root. Do not make the structured socket a TCP listener.

P10a supports one active structured client at a time. A second structured client
connection is closed immediately. Legacy control clients remain separate and
continue to use the legacy socket.

## Framing

Every structured frame starts with a fixed 24-byte little-endian header:

```text
u32 magic        "LHC2" as 0x3243484c
u16 version      1
u16 type
u16 flags        reserved, currently 0
u16 reserved     must be 0
u64 request_id
u32 payload_len
payload[payload_len]
```

Bounds:

```text
max payload          4096 bytes
structured RX frame  24 + 4096 bytes
structured TX queue  65536 bytes per client
max argv count       16
max argv bytes       4096
```

The daemon supports partial reads and writes, fragmented headers, fragmented
payloads, and multiple frames in one socket read. A bad magic/version, malformed
header, oversized payload, unknown required type, or invalid length closes or
rejects the request without unbounded allocation.

`request_id` is client-chosen for request/response correlation. `request_id=0`
is used for unsolicited/asynchronous events such as stdout/stderr/lost events.

## Handshake

Structured client state is deliberately small:

```text
NEW
  -> valid CLIENT_HELLO
READY
```

The first client frame must be:

```text
CLIENT_HELLO
```

The server replies:

```text
SERVER_HELLO
  u32 capabilities
  u32 max_payload
  u32 tx_queue_bytes
  string build_version
```

Current P10a capabilities:

```text
STATUS
EXEC
FILE
```

`FILE` is advertised only by builds that implement the path-based structured
PUT/GET operations over the existing LMUX FILE/LXF service.

Before `CLIENT_HELLO`, all non-hello operations receive a protocol error.
`SERVER_HELLO` uses the same `request_id` as the `CLIENT_HELLO`. After the
connection is READY, a duplicate `CLIENT_HELLO` is a protocol error and does
not reset the connection state. Normal request replies use the request's
nonzero `request_id`; asynchronous events use `request_id=0`.

## Error Frame

Errors and small acknowledgements use:

```text
ERROR
  u32 code
  string message
```

`code=0` means OK for request types that only need a small local acknowledgement.

Normalized codes:

```text
OK
INVALID_ARGUMENT
NOT_CONNECTED
SERVICE_UNAVAILABLE
NOT_FOUND
STALE_TARGET
BUSY
RESOURCE_LIMIT
TARGET_LOST
IO_ERROR
PROTOCOL_ERROR
INTERNAL
```

The message is diagnostic text. Clients should branch on the normalized code,
not on errno strings.

## Structured Status

`STATUS_REQUEST` returns a compact machine-readable snapshot using only state
already owned by host `lmuxd`.

The payload includes:

- host build version;
- carrier open state and byte counters;
- OUTER state, local/peer connection IDs, and selected error counters;
- LMUX state, local/peer connection IDs, and establishment count;
- factory availability bits for `pty`, `unix-rendezvous`, `file`, and `exec`;
- desired service entries with name, type, acknowledged flag, service ID, and
  internal-only flag.

The status reply is intentionally a useful stable subset, not a binary copy of
every line from `lmux status`.

## Execution References

The structured API returns an opaque host execution reference:

```text
exec_ref: u64
```

The reference is generated by host `lmuxd` and maps internally to the current
private-exec service incarnation plus target private-exec `exec_id`:

```text
exec_ref -> exec_incarnation + exec_id
```

It is not the target `exec_id`, an LMUX stream ID, a service ID, an LMUX peer
restart counter, or an MCP command token.

Properties:

- usable across OUTER/LMUX reconnect while the same worker and same `lmuxd`
  host process live;
- stale after worker replacement or target loss;
- not persistent across host `lmuxd` restart;
- never intentionally reused while the host process is running.

Structured exec event payloads may include the target `exec_id` for diagnostics,
but clients must use `exec_ref` for control requests.

The `exec_incarnation` is learned through the private exec service control
stream, not through LMUX/2 HELLO or generic `SERVICE_OK` metadata:

```text
EXEC INFO
EXEC INFO_REPLY:
  le64 exec_incarnation
```

The value is worker-local, nonpersistent, and owned by the worker exec service.

## Exec Operations

P10a structured exec operations are:

```text
EXEC_START
EXEC_ATTACH
EXEC_STATUS
EXEC_STDIN_DATA
EXEC_STDIN_CLOSE
EXEC_SIGNAL
EXEC_RELEASE
```

`EXEC_START` starts a private exec execution and attaches stdio immediately:

```text
string cwd        empty or absolute target cwd
u16 argc
string argv[argc]
```

V1 semantics:

- `argv[0]` is a direct target executable path;
- no implicit shell;
- shell behavior must be requested explicitly with `/bin/sh -c ...`;
- inherited target environment;
- no environment mutation API.

The response/event path returns:

```text
EXEC_STARTED
  u64 exec_ref
  u64 target_exec_id
  u8  state
  u8  status_kind
  u16 start_errno
  u32 exit_code
  u32 term_signal
  u32 flags
```

Ongoing state changes use `EXEC_STATE` with the same status shape. States cover
the private exec lifecycle, including starting/running, exited/signaled,
start-failed, done, and lost conditions. Process exit is not the same as output
drain; `DONE` is emitted only after the private exec service reports its final
drained state.

Stdout/stderr are byte-clean asynchronous frames:

```text
EXEC_STDOUT
  u64 exec_ref
  bytes

EXEC_STDERR
  u64 exec_ref
  bytes
```

Per-stream byte order is preserved. Cross-stream ordering is host arrival/event
ordering, not an exact target syscall interleave guarantee.

Stdin is sent as:

```text
EXEC_STDIN_DATA
  u64 exec_ref
  bytes

EXEC_STDIN_CLOSE
  u64 exec_ref
```

Accepted stdin bytes are delivered before EOF. If target stdin or the LMUX path
is backpressured, the daemon rejects additional stdin with `BUSY` rather than
building an unbounded queue.

Signals use a small symbolic enum:

```text
INT
TERM
KILL
HUP
```

The target private-exec service maps these to process-group signals.

## Attach, Disconnect, and Reconnect

Local structured client disconnect does not kill the target execution. `lmuxd`
closes the current LMUX role streams, retires the local attachment, and keeps
the `exec_ref` mapping while the same worker remains authoritative.

A later structured client can use:

```text
EXEC_ATTACH(exec_ref)
```

to attach fresh role streams to the same target execution. Only one active
attachment per execution is allowed; a competing attach returns `BUSY`.

When OUTER/LMUX disconnects while the local structured client remains connected,
the execution remains target-owned if the worker survives. After fresh
OUTER/LMUX convergence and `__exec` reconciliation, host `lmuxd` first asks the
exec service for its `exec_incarnation` using the private exec `INFO` control
record. If it matches the `exec_ref` binding, `lmuxd` automatically reattaches
the same `exec_ref` and resumes stdout/stderr/status delivery. The structured
client does not see or manage LMUX stream IDs.

If the worker is replaced, the new exec service reports a different
`exec_incarnation`. The old `exec_ref` becomes stale and the client may receive:

```text
EXEC_LOST
```

Further control using the old reference fails with a deterministic stale/not
found style error. Commands are never automatically recreated on a fresh worker.

## Backpressure

The structured socket has a bounded TX queue. If the local structured client
stops reading stdout/stderr events, `lmuxd` stops draining the corresponding
private-exec output stream once the local queue cannot accept another bounded
frame. That propagates back through LMUX flow control and the target
private-exec pipe path instead of accumulating unbounded host memory or dropping
bytes.

The same principle applies to stdin in the reverse direction: local accepted
stdin is bounded, and excess data is rejected with `BUSY` until progress occurs.

## FILE Operations

Structured FILE operations are long-running, path-based operations over the
same target FILE/LXF service used by legacy `lmux put` / `lmux get`. They do
not use shell, private exec, base64, or a second transfer protocol.

Requests:

```text
FILE_PUT_START
  string local_source_path
  string target_destination_path

FILE_GET_START
  string target_source_path
  string local_destination_path
```

All paths are absolute strings in v1. The local paths are interpreted by trusted
host `lmuxd`; target paths are sent to the target FILE service. One structured
FILE operation is active at a time for the structured client. A second start
request while one is active returns `BUSY`.

Start response:

```text
FILE_STARTED
  u64 file_op_id
  u8  kind          1=put, 2=get
  u64 expected_bytes_or_0
```

Progress is asynchronous and may be sparse:

```text
FILE_PROGRESS
  u64 file_op_id
  u64 bytes
```

Completion and failure correlate to the original request ID and include the
operation ID:

```text
FILE_DONE
  u64 file_op_id
  u64 bytes
  u8  sha256[32]

FILE_ERROR
  u64 file_op_id
  u32 code
  string message
```

PUT computes SHA256 from local bytes while streaming and verifies the target
FILE service's final digest. GET writes to a temporary host file in the
destination directory, verifies byte count and SHA256 from the target, then
renames the verified temporary file to the requested local destination. On FILE
failure, the active operation is reported with `FILE_ERROR`, temporary local
GET files are cleaned up best-effort, and `lmuxd` remains usable.

Structured client disconnect aborts any active structured FILE operation. If
OUTER/LMUX is lost during FILE transfer, the operation fails with
`TARGET_LOST`; it is not automatically reconstructed.

## Legacy Coexistence

The structured listener does not replace the existing control socket. Legacy CLI
clients and the structured client may coexist as independent local clients
subject to existing host operation serialization. The target wire, LMUX/2,
BOOT, FILE, PTY, unix-rendezvous, deployment, and private-exec target protocols
are not changed by this host API.
