# Host-Side MCP Architecture

This architecture note describes the host-side MCP frontend for LMUX Wire. The
current frontend is a standalone host process. It does not add target wire
changes, a public `lmux exec` command, or a target-side runtime. The frozen
1.0 tool surface is documented in `lmux-mcp.md` and `release-1.0.md`.

## Goals

The MCP frontend should make the existing LMUX host stack convenient for
programmatic and LLM-driven target control:

- upload a file;
- download a file;
- start a target command;
- inspect a long-running command;
- read command output incrementally;
- write command stdin;
- close command stdin;
- send explicit signals/control;
- keep stable command handles and output cursors for tool use.

Deployment:

```text
MCP client
    |
    v
lmux-mcp
    |
    v
host lmuxd / internal host API
    |
    v
LMUX services
```

`lmux-mcp` is a standalone host process. It is not loaded into the target
`lmuxd`, does not add a language runtime to the target, and does not turn
`lmuxd` into a generic RPC server.

## Implemented V1 Summary

P10b adds:

- `build/host/lmux-mcp`, a Go-only host binary;
- MCP over stdio through the official `github.com/modelcontextprotocol/go-sdk`
  transport, currently pinned at v1.8.0 with `2026-07-28` protocol support;
- an HC2 structured-control client for `/run/lmux/control-v2.sock`;
- tools for structured status, private exec commands, stdin/signals/release,
  and FILE PUT/GET;
- host-side MCP sessions, opaque command tokens, cursor-based transcript reads,
  and human-readable session journals;
- a single-instance per-user runtime owner for `$XDG_RUNTIME_DIR/lmux/mcp/`;
- default retention of five sessions and 10 MiB per session.

The implementation is intentionally a host frontend over P10a. It does not
duplicate FILE/private-exec protocols, does not call the legacy `lmux` CLI, and
does not persist sessions across `lmux-mcp` restart.

## Non-Goals

P9/P10 do not include:

- relay;
- Zeromux expansion;
- deployment redesign;
- FILE redesign;
- persistent job scheduler;
- cron;
- shell prompt parsing;
- terminal emulator;
- arbitrary RPC framework;
- target transcript database;
- target-side MCP runtime;
- auth/RBAC;
- multi-user isolation;
- remote network MCP listener by default;
- public `lmux exec` CLI.

## Component Boundaries

LMUX private exec owns target process semantics:

```text
execution
exec_id
process lifecycle
stdin/stdout/stderr
signals
exit status
detach/reattach while the same worker lives
```

MCP owns host presentation semantics:

```text
session
command_token
cursor
transcript/history
pagination
text/base64 presentation
tool result shaping
```

MCP session, command token, cursor, and transcript concepts must not be pushed
into the target wire protocol. The target remains a bounded execution primitive
with no full transcript storage.

## Session Model

`lmux-mcp` maintains host-side logical sessions:

```text
session_id
    |
    +-- command_token A
    +-- command_token B
    +-- transcript/spool state
```

V1 policy:

- `session_id` is generated by `lmux-mcp`, opaque to the MCP client, and unique
  within the lifetime of the `lmux-mcp` process.
- MCP transport connection is not the same thing as an MCP logical session.
- If the MCP framework provides a connection/session identity, `lmux-mcp` maps
  it to an internal `session_id`. If not, `lmux-mcp` creates an implicit default
  session per client connection.
- Client disconnect does not immediately kill running commands.
- A disconnected session is retained for a bounded idle grace period, initially
  10 minutes. In the current stdio deployment the process normally exits when
  the owning MCP client closes stdio, so durable cross-process session resume is
  not provided.
- Explicit session close releases all command tokens in that session and
  attempts target `RELEASE` for still-present exec objects.
- Session GC removes host transcript files and marks all command tokens stale.
- There is no durable database. Restarting `lmux-mcp` loses sessions, command
  tokens, and transcripts.

The 10-minute disconnected retention is a host policy, not a target protocol.
It is a named default and may become configurable later.

## Command Tokens

Every MCP command start returns an opaque host-side command handle:

```text
command_token
```

Rules:

- unique within one MCP session;
- never reused while the session exists;
- not an LMUX `exec_id`;
- not a LMUX `stream_id`;
- not a `service_id`;
- stale after session GC;
- stale if the mapped worker incarnation is lost;
- safe to expose to MCP clients because it carries no target internals by
  itself.

Mapping:

```text
session_id + command_token
    -> worker incarnation marker
    -> private exec exec_id
    -> host transcript state
```

The command token remains usable for reading already-spooled transcript data
even if the target execution later becomes stale due to worker replacement.
Further target control in that case fails with `STALE_TARGET`.

## Worker Incarnation Awareness

Private exec IDs are scoped to one worker incarnation. `lmux-mcp` must bind each
command token to the current worker incarnation marker known by host `lmuxd`.

If the worker is replaced, crashes, or the host observes a fresh worker
incarnation:

- commands mapped to the old worker become `LOST`;
- old `exec_id` values must not be attached to a new worker;
- already-spooled transcript remains readable until session/token GC;
- stdin, signal, status, and release operations that require the target return
  `STALE_TARGET` or `TARGET_LOST`;
- no automatic rediscovery of old target executions is attempted.

This protects against accidental attachment to a new execution that happens to
reuse the same numeric `exec_id` after worker replacement.

## Command Start Model

The primitive MCP start request is argv-based:

```text
argv: ["/bin/ls", "-la", "/tmp"]
cwd:  optional absolute target path
stdin: optional initial bytes or open stdin
```

There is no implicit shell in the primitive operation. Shell behavior is
explicit:

```text
argv: ["/bin/sh", "-c", "printf '%s\n' hello | sed 1q"]
```

Future convenience tools may expose a `shell` helper, but it must only translate
to the primitive `/bin/sh -c` form. It must not introduce prompt parsing or a
second execution model.

Environment mutation is deferred for v1. Private exec inherits the worker
environment. MCP may document this and recommend explicit shell wrappers when
the caller needs temporary environment values.

## Long-Running Commands

Command execution is not a synchronous RPC that waits until process exit.

Preferred tool shape:

```text
command_start(...) -> command_token
command_status(command_token)
command_read(command_token, cursor, max_bytes/max_records)
command_write_stdin(command_token, bytes)
command_close_stdin(command_token)
command_signal(command_token, signal)
command_release(command_token)
```

A later convenience `command_run` may start a command, wait for a small bounded
time, and return initial output plus a token. It must not block for minutes or
hours. If a convenience request is cancelled, the command continues unless the
caller explicitly requests cancellation through signal policy.

## Stdin

MCP stdin operations are byte-oriented:

```text
command_write_stdin(command_token, bytes)
command_close_stdin(command_token)
```

Rules:

- bytes are binary-safe;
- accepted bytes are delivered before EOF;
- `command_close_stdin` maps to private exec `CLOSE_STDIN`;
- closing stdin is separate from releasing the command;
- Ctrl-C is not byte `0x03`; use `command_signal(..., "INT")`.

If the target execution is already gone, stdin operations return a semantic
state error rather than silently succeeding.

## Signals

MCP exposes a constrained symbolic signal operation:

```text
command_signal(command_token, "INT")
```

V1 signals:

```text
INT
TERM
KILL
HUP
```

These map directly to private exec process-group signal semantics. Arbitrary
target signal numbers are deferred.

## Status Model

MCP command status should normalize private exec and host-side state into a
small stable vocabulary:

```text
STARTING
RUNNING
EXITED
SIGNALED
START_FAILED
LOST
RELEASED
```

Additional fields:

- `exit_code` for normal exit;
- `signal` for signaled termination;
- `start_error` for setup/exec failure;
- `target_available` boolean;
- `output_complete` boolean;
- `stdin_open` boolean;
- `transcript_start_cursor`;
- `transcript_end_cursor`;
- `lost_reason` when status is `LOST`.

`EXITED` or `SIGNALED` does not mean the transcript is exhausted unless
`output_complete` is true. This preserves the private exec invariant that child
exit must not discard already-produced stdout/stderr.

## Transcript Model

The target does not store full output. `lmux-mcp` stores host-side transcripts.

Chosen v1 model: one ordered event transcript per command.

Each transcript record:

```text
event_id / cursor position
stream = stdout | stderr | status
bytes or status payload
arrival timestamp
```

The ordering is host arrival order. Cross-stream ordering between stdout and
stderr cannot be stronger than that because the target uses separate child
pipes and separate LMUX streams. Per-stream byte order remains exact.

This model is more convenient for MCP than completely independent stdout/stderr
cursors, because a client can ask "what happened next?" with one cursor. The
stream tag still lets callers separate stdout and stderr for display or
programmatic handling.

## Binary Output Representation

Private exec is byte-clean; MCP responses must not assume UTF-8.

V1 response policy:

- every output item includes `stream` and byte length;
- if bytes are valid UTF-8 and contain no control bytes other than common
  whitespace, the response may include a `text` field;
- every item can include a `base64` field on request;
- if bytes are not safe UTF-8, the item must include `base64`;
- the transcript storage itself stores raw bytes, not JSON-escaped text.

This avoids data loss while keeping normal text command output pleasant for
tool consumers.

## Cursor Semantics

A cursor is a host-side position in a command transcript.

It is not:

- a command token;
- an LMUX stream offset;
- a target `exec_id`;
- a FILE offset;
- a byte offset in one target pipe.

V1 cursor policy:

- cursors are opaque strings in MCP responses;
- internally they may encode a monotonic transcript event index and byte
  position;
- the initial cursor is returned by `command_start`;
- `command_read` returns `next_cursor`;
- cursors remain valid while the referenced transcript range is retained;
- cursor comparison is not required from clients;
- a cursor older than the retention floor returns `CURSOR_EXPIRED`.

Conceptual read:

```text
command_read(
    command_token,
    cursor,
    max_bytes,
    max_records
)
```

Response:

```text
items
next_cursor
at_end
output_complete
truncated
```

`at_end` means no retained transcript data exists after `next_cursor` at the
moment of the read. For running commands, future output may still arrive.

## Lines And Pagination

The core transcript is byte/event-oriented, not line-oriented.

V1 required read modes:

- read from cursor with `max_bytes` and/or `max_records`;
- tail by `max_bytes`;
- report whether older output was truncated.

Line helpers such as `tail_lines=100` may be added as presentation helpers, but
line indexing is not a transport primitive and must not break binary output.
The phrase "show 100 of 1000 lines" belongs to the host/MCP presentation layer,
not to target private exec.

## Transcript Storage

Chosen v1 storage: file-backed host spool with bounded metadata in memory.

Default runtime directory:

```text
$XDG_RUNTIME_DIR/lmux/mcp/
```

`lmux-mcp` owns this per-user runtime tree. If `XDG_RUNTIME_DIR` is unavailable,
the user must pass an explicit `--runtime-dir PATH` or set
`LMUX_MCP_RUNTIME_DIR`; v1 does not silently fall back to the shared
`/run/lmux` system runtime.

Recommended layout:

```text
$XDG_RUNTIME_DIR/lmux/mcp/
    sessions/
        session-<session_id>/
            session.log
            command-<command_token>.transcript
            command-<command_token>.stdout
            command-<command_token>.stderr
    current -> sessions/session-<session_id>
```

The exact safe filename encoding for `session_id` and `command_token` is a P10
implementation detail. It must avoid path separators, control characters, and
ambiguous shell metacharacters.

Per command canonical spool may be one event transcript file or separate files:

```text
command-<token>.transcript   event metadata / cursor index
command-<token>.stdout       optional raw stdout segments
command-<token>.stderr       optional raw stderr segments
```

The exact on-disk format is implementation detail. It should be append-only for
normal output and robust against `lmux-mcp` process errors, but it is not a
durable recovery database.

Permissions:

- runtime directory owner should match the host LMUX user;
- mode should be private, for example `0700`;
- no network listener by default.

P10 default retention:

```text
retained MCP sessions:       5
storage budget per session:  10 MiB
disconnected session grace:  10 minutes
```

These are host-side MCP defaults only. They do not affect LMUX flow-control
windows, target RAM, FILE transfer size, or private-exec target buffers. They
may become configurable later, but MCP tools must not change retention policy
per request in v1.

## Human-Readable Session Journal

Every MCP logical session should also have a live host-side journal:

```text
$XDG_RUNTIME_DIR/lmux/mcp/sessions/session-<session_id>/session.log
```

This is a human observability surface for normal host tools:

```sh
tail -F "$XDG_RUNTIME_DIR/lmux/mcp/current/session.log"
lnav "$XDG_RUNTIME_DIR/lmux/mcp/current/session.log"
```

The journal is append-only by convention and updates as session events happen.
It is not a control surface. Editing, truncating, or writing to `session.log`
must not control MCP, LMUX, or the target. The canonical MCP transcript and
in-memory session state remain authoritative.

### Active Session Discovery

For the common single-agent case, `lmux-mcp` should maintain:

```text
$XDG_RUNTIME_DIR/lmux/mcp/current
```

as an atomic symlink to the most recent active session directory.

If multiple MCP clients/sessions run concurrently, P10 should avoid silent
confusion. Acceptable v1 policy:

- keep `current` for the most recent single/default session;
- create additional aliases such as `current-<safe-client-alias>` when a stable
  client/session alias exists;
- otherwise rely on the `sessions/` directory and a small human-readable index
  file such as `$XDG_RUNTIME_DIR/lmux/mcp/sessions.txt`.

No database is required. Discovery is for humans, not for protocol correctness.

### Journal Format

The journal should be line-oriented and friendly to `tail -F` and `lnav`.

Recommended v1 format: JSON Lines, with compact readable fields:

```text
{"ts":"2026-09-29T18:20:01.123+03:00","session":"s1","cmd":"c3","event":"COMMAND_START","argv":["/bin/sh","-c","ps"]}
{"ts":"2026-09-29T18:20:01.140+03:00","session":"s1","cmd":"c3","event":"STDOUT","text":"PID USER COMMAND\n"}
{"ts":"2026-09-29T18:20:01.143+03:00","session":"s1","cmd":"c3","event":"COMMAND_EXIT","code":0}
```

Exact serialization is a P10 detail, but every line should include at least:

- timestamp;
- session id or alias;
- command token when relevant;
- event/type;
- short message or payload summary.

A plain key-value format is also acceptable if it remains easy for humans to
read and for tools to filter. A binary journal is not acceptable for this
purpose.

### Journal Events

The journal should cover both MCP frontend actions and target output. Minimum
semantic events:

```text
SESSION_OPEN
SESSION_DISCONNECT
SESSION_RECONNECT
SESSION_CLOSE

COMMAND_START
COMMAND_ATTACH
COMMAND_STDIN_WRITE
COMMAND_STDIN_CLOSE
COMMAND_SIGNAL
COMMAND_STATUS
COMMAND_EXIT
COMMAND_LOST
COMMAND_RELEASE

STDOUT
STDERR

FILE_PUT_START
FILE_GET_START
FILE_OPERATION_START
FILE_OPERATION_PROGRESS
FILE_OPERATION_DONE
FILE_OPERATION_FAILED
FILE_OPERATION_CANCELLED
FILE_OPERATION_LOST

LMUX_CONNECTED
LMUX_DISCONNECTED
TARGET_WORKER_CHANGED

CURSOR_EXPIRED
RESOURCE_LIMIT
ERROR
```

The names may change during P10, but the semantics should remain visible.

File events should include source/destination paths, byte count, success/failure,
and SHA256 when the existing FILE API provides it. They must not log file
contents.

### Canonical Transcript Vs Journal

This separation is important:

- canonical command transcript is byte-clean, cursor-addressable, bounded, and
  capable of representing arbitrary binary stdout/stderr;
- `session.log` is text-oriented, line/event-oriented, intended for human
  observation and debugging;
- `session.log` is not the source of truth for MCP cursors;
- byte offsets in `session.log` are not MCP cursors;
- `session.log` is not required to preserve arbitrary binary stdout/stderr
  verbatim.

MCP cursor APIs must read from canonical transcript/spool state, never by
parsing the human journal.

### stdout/stderr In The Journal

Text output should be tagged explicitly:

```text
event=STDOUT
event=STDERR
```

Multiline textual output may be split into separate journal records where
practical. Per-stream exact bytes remain in the canonical transcript.

Binary or non-text output must not be written raw into the terminal-oriented
journal. Use summaries such as:

```text
STDOUT_BINARY bytes=4096
```

or a bounded escaped/base64 preview. Do not dump large base64 blobs into
`session.log` by default.

### stdin Privacy And Verbosity

Default journal policy for stdin is conservative:

```text
COMMAND_STDIN_WRITE bytes=N
```

For short printable input, P10 may include a bounded preview, but it should be
disabled or tightly capped by default to avoid accidental huge or sensitive
dumps. Full stdin bytes belong only to protocol/spool internals when required,
not to the human journal.

### Journal Failure Behavior

Journal failure must not corrupt LMUX transport or target state.

If `session.log` cannot be written because of disk full, permissions, or other
local errors:

- `lmux-mcp` marks session observability as degraded;
- MCP status/errors include a logging/storage diagnostic;
- canonical transcript behavior decides whether command output can still be
  retained;
- no target protocol changes or OUTER/LMUX failures are generated solely because
  the human journal failed.

If canonical transcript spool is unavailable, command observation may fail or
enter a degraded state according to the transcript policy. `lmuxd` must not
crash, and target protocol must not be reset for a host filesystem error.

### Journal Retention And Permissions

The journal lives exactly as long as the session runtime directory. Session GC
removes:

- `session.log`;
- command transcript spool files;
- session indexes/metadata.

There is no durable database. Reboot naturally clears `/run`.

Runtime directories and files should use restrictive local permissions. The
contract is:

```text
lmux-mcp writes
human tail/lnav processes observe
```

P10 should not try to make the journal immutable against the same Unix UID that
runs `lmux-mcp`; no `chattr`, root helper, or separate privilege subsystem is
part of this design.

## Host-Side Retention Policy

P10 v1 uses simple bounded retention for the per-user MCP runtime tree:

```text
max retained sessions:       5
max storage per session:     10 MiB
```

Both values are named defaults and may become configurable later, conceptually
through process configuration such as `--max-sessions` or
`--max-session-bytes`. Exact CLI/config names are deferred. MCP tools do not
change retention policy per request in v1.

### What Counts Toward 10 MiB

The per-session 10 MiB budget applies to logical storage owned by:

```text
$XDG_RUNTIME_DIR/lmux/mcp/sessions/session-<session_id>/
```

It includes:

- canonical command transcript spool;
- `session.log` and rotated journal segment;
- small session metadata/index files.

It does not include external files transferred through the LMUX FILE service.
Small filesystem block/accounting overhead is acceptable; the limit is a
logical payload/storage budget, not a requirement that `du` equal exactly
10485760 bytes.

### Global Retained-Session Limit

At most five session directories are retained by default.

When P10 needs to create or retain a sixth session:

1. find the oldest eligible non-active session;
2. remove its whole session directory, including transcript spool, journal,
   rotated journal segment, metadata, and indexes;
3. update active-session discovery pointers if needed;
4. create the new session.

Eviction order must be deterministic. Preferred ordering is by a monotonic
session lifecycle sequence maintained by `lmux-mcp`, using finalized/last-active
order. Do not rely on filesystem directory iteration order or target wall
clock.

### Active Sessions Are Not Auto-Evicted

Automatic retention cleanup must never delete an active MCP session.

A session is active when any of these is true:

- an MCP client is currently attached;
- it has running commands;
- it is still within the disconnected-session grace period.

After explicit close, or after the disconnected grace expires and no running
work remains, the session becomes eligible for retention eviction.

If all five retained sessions are active/non-evictable, a new session fails with
`RESOURCE_LIMIT` and a clear detail such as "retained session limit contains
only active sessions". P10 must not silently kill commands, delete transcripts,
or break a live Codex/MCP connection to make room.

### Per-Session Overflow

If an active session reaches its 10 MiB storage cap, P10 must not delete the
active session. Instead it uses the transcript retention policy:

- continue draining target stdout/stderr;
- discard oldest retained canonical transcript data first;
- advance the transcript retention floor;
- keep command identity/status objects for running commands;
- return `CURSOR_EXPIRED` for cursors below the new floor.

Transcript eviction is not command release. It must not remove the ability to
status, signal, stdin-close, or release a still-running command.

### Within-Session Priority

Storage pressure inside a session follows this priority:

1. preserve small current session metadata and command identity/status objects;
2. preserve recent canonical command transcript;
3. discard oldest canonical transcript data first, on complete record/chunk
   boundaries;
4. keep the human journal bounded as secondary observability data.

The canonical transcript is the primary MCP storage. The human journal must not
consume the whole 10 MiB and squeeze out practically all cursor-addressable
transcript.

P10 v1 journal sub-budget:

```text
session.log current segment: 512 KiB
session.log.1 previous:      512 KiB
total journal budget:        about 1 MiB per session
canonical transcript/meta:   remaining session budget
```

### Journal Rotation

Preferred v1 journal bounding uses two files:

```text
session.log       current
session.log.1     previous bounded segment
```

When `session.log` reaches its segment cap, `lmux-mcp` rotates it to
`session.log.1` and opens a fresh `session.log`. Only one previous segment is
kept. Recent events remain easy to inspect, old journal events may be dropped,
and canonical transcript cursors are unaffected.

This is compatible with `tail -F` and `lnav` because new events continue to
arrive in the current pathname. Journal rotation is observability only; it must
not affect command execution.

### Canonical Transcript Eviction Granularity

Eviction must never delete random bytes from the middle of a transcript record.

If P10 uses a unified event transcript, it advances `retention_floor` to the
next complete event. If it uses per-command spool files, the same invariant
applies at the chosen record/chunk boundary. stdout/stderr metadata must remain
parseable after truncation.

### Command Release

`command_release` may immediately remove:

- command transcript storage;
- command-specific metadata that is no longer required;
- target private exec metadata, when the target execution still exists.

The freed bytes return to the session budget. `session.log` may retain a small
`COMMAND_RELEASE token=...` event until normal journal rotation drops it.

### Session Deletion

Session eviction or GC removes the whole runtime tree:

- canonical transcript spool;
- `session.log`;
- rotated journal segment;
- metadata/index files.

No orphan files should remain. If `current` or another discovery symlink points
at the session being removed, P10 should atomically retarget it to another
active/recent session or remove it. Avoid dangling discovery state where
practical.

### Startup Cleanup And Ownership

P10 v1 should use a single-instance ownership model:

```text
one lmux-mcp instance owns $XDG_RUNTIME_DIR/lmux/mcp/
```

A second instance should fail with a clear already-running/resource error
rather than race the global five-session cleanup. This is the simplest safe
default for Codex-launched `lmux-mcp`.

Startup should clean stale `$XDG_RUNTIME_DIR/lmux/mcp` state from an abnormal
previous exit. The runtime tree is non-durable host state, so durable recovery
is not required.
Use an ownership marker such as a pid plus process-generation/lock file to
distinguish:

- state owned by the current live `lmux-mcp`;
- stale state from a dead process;
- a live other instance, which must not be deleted.

Do not build a persistent database or crash-recovery journal.

## Overflow Policy

Chosen v1 overflow policy: host-side oldest-output truncation with explicit
cursor expiration.

When a command exceeds its retained transcript limit:

- `lmux-mcp` continues draining target stdout/stderr;
- oldest transcript records are dropped from the readable retention window;
- the command transcript records a truncation marker;
- `transcript_start_cursor` advances;
- reads from older cursors fail with `CURSOR_EXPIRED`;
- the response includes the new earliest cursor.

This policy keeps target commands from blocking merely because an MCP client is
not reading quickly enough, while preserving an honest signal that history was
lost. It trades exact full-output retention for bounded host disk and better
long-running command behavior.

If a future caller needs lossless full-output capture, that should be an
explicit command option with a different limit/backpressure policy. It is not
the default v1 behavior.

The active session journal should record cleanup events that affect the current
session, for example:

```text
TRANSCRIPT_TRUNCATED old_floor=... new_floor=... bytes_reclaimed=...
```

Global removal of an old inactive session may be recorded in a small
process-level daemon journal or status file if P10 adds one, but that is not a
new logging subsystem requirement.

## Cursor Expiration

If a client reads from a cursor older than the retention floor:

```text
CURSOR_EXPIRED
earliest_cursor = ...
```

The server must not silently jump forward and pretend output was continuous.
The caller may decide to continue from `earliest_cursor`.

## File Operations

MCP file tools use the existing FILE service. They must not reimplement file
transfer through shell, exec, base64, or private exec.

The original blocking tools remain available:

```text
file_put(local_source, target_destination)
file_get(target_source, local_destination)
```

The FILE service already provides PUT/GET and SHA-verified transfers in the
LMUX stack. MCP surfaces those operations through the host internal API and
waits for structured FILE completion before returning byte count and SHA256.
They now honor the MCP request context. If that context expires after start,
the returned error includes the operation ID and explicitly says to query
status before retrying; the daemon-owned transfer is not automatically retried
or implicitly cancelled.

Post-1.0 long-running helpers are:

```text
file_put_start(local_source, target_destination, request_token)
file_get_start(target_source, local_destination, request_token)
file_operation_status(operation_id | request_token)
file_operation_wait(operation_id, timeout_ms)
file_operation_cancel(operation_id)
```

`request_token` is caller-supplied and known before START. The host key is the
pair of the private MCP session namespace and this token. A retained duplicate
with identical direction and paths returns the original operation; a parameter
conflict is rejected. Status by token finds RUNNING and retained terminal
results, including when the START response was lost. Status with neither ID nor
token remains an active-operation diagnostic only.

`operation_id` is an opaque decimal string in MCP JSON so a 64-bit ID is never
rounded by a JSON/JavaScript client. Status returns direction, paths, `RUNNING |
DONE | FAILED | CANCELLED | LOST`, byte progress, total size when known, LMUX
incarnation, and the terminal error or SHA256. Wait defaults to 15 seconds, is
capped at 20 seconds, accounts for the MCP context deadline with a response
reserve, and uses terminal notifications plus an authoritative final status
read instead of busy polling. Local expiry returns `RUNNING` plus
`wait_timed_out=true`. Cancel returns the authoritative state; a transport
failure during cancel is reported as an unknown cancellation result.

The synchronous `file_put` and `file_get` results retain `file_op_id` as a
deprecated compatibility alias. In 1.0.1 it is also a decimal JSON string,
identical to `operation_id`; consumers must not expect a JSON number. New code
should use `operation_id`. This type correction prevents JavaScript-style JSON
consumers from rounding randomly seeded 64-bit operation IDs above `2^53-1`.

Keyed results use the bounded eight-entry daemon history. Lookup after eviction
or daemon restart returns `UNKNOWN`, `outcome_ambiguous=true`, and a warning;
absence must not be treated as permission to retry. The guarantee survives HC2
reconnect within one MCP/daemon lifetime, not process restart. A concurrent
start `BUSY` diagnostic includes the active operation ID.

These tools use the same host FILE engine and target LXF service. They do not
create a general remote filesystem RPC framework.

Optional future helpers may expose remote SHA/status if supported cleanly by
the existing FILE service or a documented extension. P9 does not require a new
FILE wire protocol.

## PTY Boundary

MCP command execution uses private exec, not PTY.

PTY remains for human interactive terminal semantics:

```text
terminal modes
winsize
job control
Ctrl-C as terminal input
interactive shell behavior
```

Private exec remains for programmatic commands:

```text
direct argv
separate stdout/stderr
explicit signals
binary-safe pipes
host transcript
```

A future MCP `pty_attach` tool may wrap the existing PTY service, but it is not
part of P10 command execution.

## Host Internal API Boundary

`lmux-mcp` should communicate with host `lmuxd` through a structured local
control API.

P10a decision:

```text
lmux-mcp
    -> dedicated structured host-control Unix socket
    -> reconciled services (__exec, files, status)
```

Reasons:

- `lmuxd` already owns carrier, OUTER, LMUX, desired service reconciliation, and
  the private `__exec` service;
- `lmux-mcp` should remain a separate process;
- in-process library embedding would duplicate lifecycle ownership;
- the existing human text control socket remains optimized for current CLI
  behavior;
- a dedicated structured listener avoids a fragile mixed text/binary parser on
  the legacy socket while still using the same `lmuxd` process and same poll
  loop.

The current human text control protocol is useful for CLI and tests, but P10
adds structured internal operations for MCP use rather than parse
human-oriented text. The P10a implementation documents this local binary
protocol in `docs/host-control.md`.

The internal API should cover:

- status snapshot;
- private exec start/status/read/write-stdin/close-stdin/signal/release;
- FILE put/get through the existing FILE/LXF service using path-based
  asynchronous operations;
- service availability and worker incarnation marker.

It should remain local-only and permissioned by the Unix socket/runtime
directory. No remote network MCP listener is introduced by default.

## MCP Process And Source Placement

Implemented source placement:

```text
cmd/lmux-mcp/
internal/hc2/
internal/mcpapp/
```

`cmd/lmux-mcp/` contains the standalone MCP frontend. `internal/hc2/` contains
the structured host-control client. `internal/mcpapp/` contains session,
transcript, retention, and journal state.

The implementation is a standalone Go `lmux-mcp` process. The C host daemon
remains the owner of LMUX runtime state.

Host control protocol extensions remain in the current C tree near the existing
host control implementation.

## Tool Surface

Minimal MCP tool surface:

```text
lmux_status

file_put
file_get
file_put_start
file_get_start
file_operation_status
file_operation_wait
file_operation_cancel

command_start
command_status
command_read
command_write_stdin
command_close_stdin
command_signal
command_release
```

Optional later convenience:

```text
command_run
```

`command_run` must be bounded and return a token if the command is still
running or output remains unread. It is a convenience wrapper, not the core
lifecycle.

Avoid a large tool list in v1. Higher-level workflows can compose these
primitives.

## Session API

V1 does not require public `session_open` / `session_close` tools if the MCP
framework provides a natural client/session context.

Internal policy:

- every command belongs to a session;
- sessions can be explicitly closed through a management path if the MCP
  framework supports it;
- otherwise disconnection plus bounded GC is sufficient;
- command tokens are scoped to a session;
- clients cannot use a token from another session.

If an explicit session tool is added later, it should expose only host-side
session lifecycle, not target state.

## Concurrency

One MCP session may own multiple simultaneous commands.

Limits:

- target private exec running limit still applies;
- host transcript limits still apply;
- control API should return `RESOURCE_LIMIT` or `BUSY` rather than serialize all
  commands artificially;
- per-command operations may proceed independently, subject to LMUX/service flow
  control.

P10 should avoid one global "current command" model.

## Cancellation And Disconnect

MCP request cancellation is not process cancellation.

Examples:

- cancelling `command_read` stops that read request only;
- command keeps running;
- transcript collection continues while limits allow;
- caller must use `command_signal` to interrupt/terminate target process;
- client disconnect keeps the session for the bounded retention period.

If a future `command_run` convenience is cancelled, the command should continue
and remain addressable by its token unless the request included an explicit
`kill_on_cancel` style option. That option is deferred.

## Cleanup And Release

Command lifecycle:

```text
START
RUNNING
FINAL target state
RELEASE
```

`command_release`:

- closes MCP command token state;
- removes transcript/spool files for that command;
- sends target private exec `RELEASE` if the target execution is still present;
- succeeds idempotently for already-released host state when possible;
- if the target is already lost, still cleans host state and reports target
  cleanup as skipped/lost.

Session GC releases all command tokens in the session. Global spool GC may
truncate transcripts according to the overflow policy, but it must not silently
reuse command tokens.

## Persistence

There is no durable MCP persistence in v1.

After `lmux-mcp` restart:

- sessions are gone;
- command tokens are gone;
- transcripts are gone or cleaned as stale runtime files;
- target executions may technically still exist if the worker survived, but
  automatic rediscovery is not required.

After host `lmuxd` restart:

- `lmux-mcp` loses its control connection;
- target private exec objects may or may not survive depending on worker
  lifecycle;
- P10 may mark active commands `TARGET_LOST` until a fresh status proves the
  same worker incarnation and same exec still exist;
- automatic transaction reconstruction is not required.

This keeps P10 out of persistent job-management territory.

## Error Model

MCP should normalize common errors:

```text
NOT_CONNECTED
SERVICE_UNAVAILABLE
NOT_FOUND
STALE_TARGET
BUSY
INVALID_ARGUMENT
CURSOR_EXPIRED
RESOURCE_LIMIT
TARGET_LOST
TRANSCRIPT_TRUNCATED
STORAGE_DEGRADED
INTERNAL
```

Responses may include diagnostic detail:

```text
errno
target_error
lmux_state
message
```

but clients should not need to parse raw errno strings as the primary API.

Retention eviction is not a storage failure. Important cases:

- `RESOURCE_LIMIT`: a new session cannot be created because the five retained
  session slots are occupied only by active/non-evictable sessions.
- `CURSOR_EXPIRED`: requested cursor points before the current retention floor.
- `STORAGE_DEGRADED`: host spool/journal cannot maintain normal storage because
  of a filesystem error, permission problem, or real disk-full condition.

Configured 10 MiB/session retention does not guarantee that the host filesystem
has free space. On `ENOSPC` or similar storage errors, `lmux-mcp` should:

- keep command/control state coherent where possible;
- stop promising transcript bytes that were not physically retained;
- report degraded storage state through MCP status/errors;
- avoid crashing `lmuxd`;
- avoid resetting target protocol solely because host storage failed.

If canonical transcript spool cannot accept new data, P10 may have to mark the
command observation degraded and continue only with best-effort recent state.
It must not pretend that missing transcript data is available.

## Observability

`lmux_status` should return a structured subset of existing host status:

- carrier configured/open state;
- OUTER enabled/state/counters;
- LMUX established/recreation marker;
- worker incarnation marker when available;
- service availability for `files` and `__exec`;
- desired service reconciliation state;
- active MCP sessions/commands count from `lmux-mcp`.

It should not return only the human `lmux status` text blob. It also should not
require new target wire solely for MCP observability.

Human observability is also a supported host-side feature. A user should be
able to open `tail -F` or `lnav` on the current session journal before or
during Codex/agent work and see session events, command output summaries, file
actions, and target connectivity changes as they happen. This requires no MCP
client connection and no new LMUX protocol/service.

## Security

LMUX currently assumes a trusted host. MCP exposes arbitrary target process
execution and file transfer, so the host surface must be intentionally local.

V1 security policy:

- bind only local Unix sockets by default;
- private runtime directories, e.g. mode `0700`;
- no unauthenticated network listener;
- no target-side auth/RBAC;
- no multi-user isolation promise;
- deployment-specific access control belongs to the host environment.

This is not a security platform. It is a trusted-host embedded control frontend.

## P10 Implementation Scope

Recommended split:

### P10a: Structured Host Control API

- Add a dedicated structured local host-control listener in host `lmuxd`.
- Add framed, versioned, binary-safe operations for status and private exec.
- Add asynchronous path-based structured FILE PUT/GET over the existing
  FILE/LXF service, with operation IDs, progress, byte counts, and SHA256
  results.
- Preserve existing human CLI/control behavior.
- Expose worker incarnation markers to host clients.
- Keep `__exec` internal-only, no public `lmux exec`.
- Provide binary-safe stdin/stdout/stderr transport between `lmux-mcp` and
  `lmuxd`.

### P10b: Standalone `lmux-mcp`

- Add standalone `lmux-mcp`.
- Implement session and command token management.
- Implement file-backed transcript spool under `$XDG_RUNTIME_DIR/lmux/mcp`.
- Implement per-session runtime directories.
- Implement live human-readable `session.log`.
- Implement active-session discovery via `current` symlink, `current-<alias>`,
  or equivalent index.
- Implement default retention:
  - maximum retained sessions: 5;
  - maximum logical storage per session: 10 MiB.
- Implement single-instance ownership for `$XDG_RUNTIME_DIR/lmux/mcp/` and startup cleanup
  of stale runtime directories.
- Implement cursors, reads, tail reads, and cursor expiration.
- Implement command start/status/stdin/close/signal/release.
- Implement FILE put/get tools through structured host control.
- Implement bounded cleanup and disconnected session GC for transcript spool and
  journals.
- Implement structured `lmux_status`.

P10 explicitly does not add:

- public `lmux exec`;
- target transcript spool;
- persistent job database;
- auth/RBAC;
- terminal emulator;
- deployment redesign.

## P10 Test Plan

Command lifecycle:

- start `/bin/true`;
- observe running/final status;
- release token;
- repeated release is deterministic.

Long running:

- start command that runs while other status/read requests proceed;
- later read output and final status.

Cursor:

- read partial output;
- resume with returned cursor;
- no duplicate records;
- no skipped retained records.

Cursor expiration:

- exceed per-command transcript retention;
- old cursor returns `CURSOR_EXPIRED`;
- earliest cursor is returned.
- cursor at or after the retention floor continues correctly.

Retention:

- sixth retained session evicts the oldest inactive eligible session;
- active session is never auto-evicted;
- five active/non-evictable sessions make a sixth session return
  `RESOURCE_LIMIT`;
- a session exceeding 10 MiB advances transcript retention floor;
- command identity/status survives transcript truncation;
- command release reclaims storage budget;
- session GC removes the whole directory tree;
- `current`/session discovery survives eviction cleanly;
- startup cleanup removes stale runtime directories from a dead previous
  `lmux-mcp`;
- cleanup never touches files transferred through the FILE service.

stdout/stderr:

- output records include correct stream tags;
- host arrival order is stable;
- per-stream bytes are exact.

Binary output:

- arbitrary bytes roundtrip through base64 representation;
- valid UTF-8 text may be represented as text without losing bytes.

Signals:

- INT/TERM/KILL map to private exec signal operations;
- stale target returns `STALE_TARGET`.

stdin:

- write bytes;
- close stdin;
- child observes data before EOF.

MCP disconnect:

- command survives client disconnect during retention window;
- session GC later releases host resources.

Worker replacement:

- command token becomes `STALE_TARGET` or `LOST`;
- old transcript remains readable until session/token GC;
- no attach to a new worker exec with reused numeric ID.

FILE:

- put target file through existing FILE service;
- get target file through existing FILE service;
- no shell/base64 transfer path.

Journal:

- command start/output/exit appears in `session.log` in order;
- stdout and stderr are tagged distinctly;
- binary output produces summaries/previews and does not corrupt the human
  journal;
- signal actions appear;
- file put/get events appear with paths, byte counts, and result;
- worker replacement/lost command appears;
- concurrent sessions do not overwrite each other's journals;
- session GC removes journal and spool files;
- journal rotation/bounding preserves live tailability;
- journal retention never corrupts canonical cursor storage;
- journal writer handles partial writes/errors without corrupting MCP state;
- observer opening/reading the journal has no effect on command execution.

Storage errors:

- ENOSPC or permission failure reports `STORAGE_DEGRADED`;
- storage failure does not crash `lmuxd`;
- configured retention eviction is not reported as disk-full failure.

Concurrency:

- multiple command tokens in one session;
- target running limit produces `RESOURCE_LIMIT`.

Cleanup:

- command release removes transcript files;
- session GC removes all session files;
- global spool limit enforces truncation/GC.

Regression:

- PTY, FILE, private exec, OUTER, BOOT, deploy, and service reconciliation stay
  green.

## Unresolved Questions

These should be decided during P10 implementation, not by changing target wire:

1. Exact spool file format. Recommendation: append-only event index plus raw
   per-stream byte blobs.
2. Exact logical storage accounting details inside the fixed 10 MiB session
   budget, including how metadata bytes and partially rotated journal segments
   are counted.
3. Whether to expose explicit session tools. Recommendation: start implicit,
   add explicit session management only if the MCP framework/user experience
   needs it.
4. Exact factoring boundary between legacy CLI FILE helpers and the structured
   daemon-owned FILE operation code can still be cleaned up, but the P10a
   semantic decision is fixed: both paths use the same target FILE/LXF service,
   and the structured API remains asynchronous and bounded.
